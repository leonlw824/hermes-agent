## 1. 项目概述

### 1.1 一句话定位

> **一个让企业像搭建 SaaS 一样搭建 AI 员工的平台。**  
> 企业管理员通过 Web 对话或点击配置，创建、发布和管理公司的"智能体员工"(Agent)，员工和外部系统通过对话或 API 使用这些 Agent。

### 1.2 核心价值主张

| 角色 | 痛点 | ArchForge 解法 |
|------|------|---------------|
| **CEO/企业主** | AI 项目落地难，不懂技术，无法管控 AI 使用成本和安全 | 中心化管理后台，一人配置全司可用，统一成本管控 |
| **IT 管理员** | 多个 Agent 分散管理，权限混乱，知识库各自为政 | 统一知识库，RBAC 权限，审核发布流程，用量可视化 |
| **业务团队** | 不会写代码，但需要 AI 辅助日常工作 | 对话式 Agent 创建，像聊天一样搭建 AI 助手 |
| **开发者** | 需要将 AI 能力集成到自有系统 | 标准 REST API + API Key 授权机制 |

### 1.3 目标用户画像

**P0 — 核心用户（MVP 必须覆盖）**

1. **企业超级管理员 / IT Director** — 35-50 岁，决策者，关注安全、成本、ROI。使用 Web 控制台搭建组织架构、管理 Agent、查看统计。
2. **团队负责人 / 业务主管** — 30-45 岁，一线管理者，关注团队效率提升。创建团队级 Agent、配置知识库、管理成员权限。
3. **普通员工（Agent 使用者）** — 22-45 岁，一线员工，关注 Agent 是否好用。通过对话界面使用 Agent，无需任何配置。

**P1 — 重要用户（迭代支持）**

4. **开发者 / 系统集成工程师** — 25-40 岁，技术背景。通过 API 对接 Agent 到公司内部系统。

**P2 — 长期用户**

5. **平台运营人员（ArchForge 内部）** — 管理平台级配置、审核、监控平台健康度。

### 1.4 项目目标

- **MVP 目标**: 3 个月内上线，支持 1 个企业创建 10 个 Agent，每个 Agent 日处理 1000 次对话
- **6 个月目标**: 服务 50 家企业客户，单企业支持 100+ Agent
- **12 个月目标**: 千企规模，Agent 日对话量百万级

### 1.5 关键成功指标 (KSF / OKR)

| 指标 | MVP 目标 | 计算方法 |
|------|---------|---------|
| **Agent 创建完成率** | > 80% | 开始创建到发布成功的比例 |
| **Agent 对话满意度** | > 3.8/5 | 对话后用户反馈评分 |
| **API 请求成功率** | > 99.5% | 成功响应 / 总请求 |
| **管理后台任务完成时长** | < 3min/任务 | 从登录到完成一个典型操作(创建Agent、配置知识库等) |
| **部署时间 (首次创企)** | < 10min | 从注册到第一个 Agent 上线 |

## 2. 功能架构 — 信息效率视角

### 2.1 核心原则

> **信息效率 = 单位操作路径长度 的倒数 × 信息密度**  
> 产品设计的本质是降低用户获取信息和完成任务的信息熵。

以张一鸣的"信息效率"视角，将功能按用户心智负担和操作频率分层：

### 2.3 功能分层与北极星指标对齐

| 层级 | 北极星指标 | 信息效率策略 |
|------|-----------|-------------|
| Layer 1 | 日活跃对话数 (DAU Conv) | 零点击进入对话，隐藏系统复杂度 |
| Layer 2 | Agent 创建完成率 | 对话式引导 + 模板化，一次成功 |
| Layer 3 | 组织搭建完成率 | 树状可视化 + 批量操作 + 默认继承 |
| Layer 4 | 配置完整度 | 渐进式披露，默认值最优 |
| Layer 5 | API 集成成功率 | 自服务 + 即时代码示例 |

## 3. 页面结构

### 3.1 页面清单 (MVP 版本)

> 以信息效率原则，MVP 页面总数控制在 **12 个以内**，每个页面聚焦一个核心任务。

#### 3.1.1 公共页面 (无鉴权)

| 页面 | 路由 | 功能 | 优先级 |
|------|------|------|--------|
| 登录/注册 | `/login`, `/register` | 邮箱+密码登录，支持 SSO (企业版) | P0 |
| 密码重置 | `/reset-password` | 邮件验证重置 | P1 |

#### 3.1.2 对话界面 (Layer 1 — 最高频)

| 页面 | 路由 | 功能 | 优先级 |
|------|------|------|--------|
| **Agent 市场** | `/agents` | 展示当前用户可用的 Agent 列表，支持搜索和分类 | P0 |
| **Agent 对话** | `/agents/:id/chat` | 对话界面：消息列表 + 输入框 + 流式输出 + 历史会话侧栏 | P0 |
| 对话历史 | `/agents/:id/chat?history=:sessionId` | 查看/继续历史对话 | P0 |

**关键交互细节**:
- Agent 市场按"我最近使用的 → 团队推荐的 → 全部"排序
- 用户首次进入，推荐 1-3 个"热门 Agent"
- 对话界面默认右侧显示 Agent 信息卡片（名称、描述、能力标签）

#### 3.1.3 管理控制台 (Layer 2-4 — 管理员)

| 页面 | 路由 | 功能 | 优先级 |
|------|------|------|--------|
| **工作台首页** | `/console` | 概览：Agent 总数、今日对话量、Token 消耗、最近审核、快速操作 | P0 |
| **Agent 管理** | `/console/agents` | Agent 列表（状态过滤、搜索、批操作），新建入口 | P0 |
| **Agent 创建/编辑** | `/console/agents/new` | 双模式创建：对话式创建 + 表单模式 | P0 |
| | `/console/agents/:id/edit` | | |
| **Agent 详情** | `/console/agents/:id` | 概览、版本历史、绑定知识库、API Key 管理、用量统计 | P0 |
| **团队管理** | `/console/teams` | 树形团队结构、成员管理、角色分配 | P0 |
| **知识库管理** | `/console/knowledge` | 知识库列表、上传文档、检索测试 | P0 |
| **使用统计** | `/console/stats` | Token 用量趋势、Agent 排行、模型分布 | P0 |

#### 3.1.4 系统设置 (Layer 4 — 专业角色)

| 页面 | 路由 | 功能 | 优先级 |
|------|------|------|--------|
| **公司设置** | `/console/settings/company` | 公司信息、套餐、时区、品牌 | P1 |
| **模型配置** | `/console/settings/models` | 可用模型列表、Provider 配置、默认参数 | P1 |
| **角色权限** | `/console/settings/roles` | 角色列表、权限矩阵配置 | P1 |
| **成员管理** | `/console/settings/members` | 全公司成员列表、批量邀请、角色分配 | P1 |
| API Key 管理 | `/console/settings/api-keys` | 全局 API Key 概览（平台级） | P2 |

### 3.2 页面设计原则

1. **最小操作路径**: 任何核心任务不超过 3 次点击到达
2. **渐进披露**: 高级功能默认折叠，用户需要时再展开
3. **一键复用**: Agent 模板、知识库绑定、角色模板支持"从已有复制"
4. **预览优先**: 配置过程实时预览效果（如 Prompt 测试）
5. **失败友好**: 配置出错时给出具体修复建议，而非通用错误码

## 4. 功能优先级与迭代规划

### 4.1 MVP 定义原则

> **做减法 → 只做 20% 的功能解决 80% 的需求**  
> 三个过滤条件:
> 1. 没有这个功能，核心业务流程能否跑通？
> 2. 这个功能能否用人工流程代替？
> 3. 推迟 3 个月做，会流失多少用户？

### 4.2 MVP 功能集 (Phase 1 — 0-3 个月)

```
核心链路: 注册公司 → 创建团队 → 搭建 Agent → 知识库绑定 → 
          审核发布 → 员工对话使用 / API 调用

F1 [P0] 公司注册与管理
  ├── 注册/登录 (邮箱+密码)
  ├── 公司信息设置
  └── 套餐基础版 (10 Agent, 1000次对话/日, 1GB知识库)

F2 [P0] 团队管理 (简化版)
  ├── 创建团队 (单层, 无子团队)
  ├── 添加成员 (邮箱邀请)
  └── 成员角色分配 (预置角色)

F3 [P0] Agent 搭建 (双模式)
  ├── 对话模式: "我想要一个客服助手..." → AI 自动生成
  ├── 表单模式: 名称 + 头像 + System Prompt + 模型选择
  ├── 模型绑定 (平台预置模型池, 不支持 BYOK)
  └── 保存为草稿 / 提交审核

F4 [P0] 知识库绑定 (基础版)
  ├── 创建知识库 (名称+描述)
  ├── 上传文档 (PDF/MD/TXT, 单文件 < 10MB)
  ├── 自动分块 + 向量化 (默认参数, 不可调)
  └── 绑定到 Agent (多对多)

F5 [P0] 审核发布机制 (简化版)
  ├── Agent 状态机: 草稿 → 待审核 → 已通过 → 已发布
  ├── 公司管理员可审核 (平台运营兜底)
  ├── 审核界面: Prompt 预览 + 知识库检查
  └── 版本号: 自动递增 (v1, v2...)

F6 [P0] 对话界面
  ├── Agent 市场列表 (用户可见的已发布 Agent)
  ├── 对话输入 + 流式输出
  ├── 上下文记忆 (单会话)
  └── 对话历史 (最近 30 条)

F7 [P0] API 对接 (基础版)
  ├── 生成 API Key (自动生成, 不可自定义)
  ├── API Key 列表 (仅显示前缀和后 4 位)
  ├── API 认证 (Header X-API-Key + HMAC-SHA256)
  └── 对话 API: POST /v1/agents/:id/chat

F8 [P0] 基础统计
  ├── 工作台概览 (Agent数 / 今日对话 / Token 消耗)
  ├── Token 用量趋势图 (按日)
  └── Agent 使用排行 (按对话次数)

F9 [P0] 权限体系 (基础版)
  ├── 预置角色: 超管、公司管理员、开发者、成员
  ├── 功能权限: agent:create, agent:edit, agent:approve
  └── Agent 权限: 谁可以对话、谁可以管理
```

### 4.3 Phase 2 迭代 (3-6 个月)

```
功能方向: 深度化 + 企业级特性

I1 [P1] 高级知识库
  ├── 文档格式扩展 (DOCX, CSV, HTML, JSON)
  ├── 自定义分块策略 (大小 / 重叠 / 分隔符)
  ├── 手动触发重新索引
  ├── 知识库版本管理
  └── 检索测试工具 (Query → Top-K 预览)

I2 [P1] 高级模型配置
  ├── BYOK (Bring Your Own Key)
  ├── 模型 fallback 配置 (主模型 → 备用模型)
  ├── 自定义模型参数 (temperature, top_p, max_tokens)
  └── 模型路由 (按成本/延迟策略)

I3 [P1] 团队树形层级
  ├── 多级子团队 (Company → Dept → Team)
  ├── 权限继承 + 显式覆写
  └── 团队级知识库隔离

I4 [P1] 对话增强
  ├── Agent 技能 / 工具 (函数调用)
  ├── 文件上传对话 (PDF 解读)
  ├── 对话分支 (从某条消息分叉)
  └── 对话导出 (Markdown / JSON)

I5 [P1] API 增强
  ├── 多 API Key (主/备轮换)
  ├── IP 白名单
  ├── 速率限制 (按 Key 配置)
  └── API Key 过期时间

I6 [P1] 统计增强
  ├── 按团队/Agent/模型/API Key 下钻
  ├── Token 成本估算
  ├── 导出 CSV/PDF
  └── 告警规则 (预算超支、异常流量)
```

### 4.4 Phase 3 迭代 (6-9 个月)

```
功能方向: 开放平台 + 商业化

I7 [P2] Agent 技能市场
  ├── 内置技能 (计算器、搜索、日期等)
  ├── 自定义技能 (OpenAPI 声明)
  └── 技能商店 (社区贡献)

I8 [P2] SSO / 企业集成
  ├── OAuth2 / SAML / LDAP
  ├── 企业微信 / 飞书 / Slack 集成
  ├── Webhook 事件通知
  └── Agent 嵌入 (iframe SDK)

I9 [P2] 桌面 Agent 运行时 (看第 6 节决策)
  ├── Tauri 轻量客户端
  ├── 本地文件系统操作
  └── 离线执行 + 审计回传

I10 [P2] 高级安全特性
  ├── 操作审计日志 (全量)
  ├── Prompt 注入检测
  ├── 敏感内容扫描
  └── SOC 2 报告导出
```

### 4.5 迭代节奏策略

| 阶段 | 周期 | 发布节奏 | 验证方式 |

| Phase 2 | 3-6 月 | 每 3 周一个 Release | 50 家企业 Beta |
| Phase 3 | 6-9 月 | 每月一个 Release | 正式商业化 GA |

## 5. 用户角色与权限设计

### 5.1 全局角色体系

```
平台级 (ArchForge 运营)
└── platform_admin        平台超级管理员，管理所有企业、模型池、套餐

企业级 (客户公司内)
├── company_admin         公司管理员，管理公司设置、团队、所有 Agent
├── team_lead             团队负责人，管理本团队 Agent 和成员
├── developer             开发者，创建/编辑 Agent，不可审核发布
├── member                普通成员，可使用被授权的 Agent
└── api_user              API 用户，仅通过 API 使用 Agent，无控制台权限
```

### 5.2 权限矩阵 (MVP)

| 权限点 | platform_admin | company_admin | team_lead | developer | member | api_user |
|--------|:--------------:|:-------------:|:---------:|:---------:|:------:|:--------:|
| **公司管理** | | | | | | |
| 查看公司信息 | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| 编辑公司设置 | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ |
| 管理套餐 | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ |

### 5.3 Agent 级数据权限模型

Agent 的"可见/可用"范围独立于功能权限，通过 ACL 控制：

```
Agent 可见范围:
  - public: 公司内所有人可见
  - team: 仅指定团队可见（团队成员自动获得）
  - restricted: 仅指定成员可见

Agent 操作权限 (每个成员独立 ACL):
  - owner: 完全控制 (编辑/删除/授权/审核)
  - editor: 可编辑配置但不可发布
  - user: 仅可使用（对话/API）
  - none: 不可见不可用
```

### 5.4 权限继承规则

```
公司管理员
  └── 自动获得所有团队和 Agent 的管理权限

团队负责人
  └── 自动获得本团队所有 Agent 的 owner 权限
  └── 子团队默认继承父团队的 Agent 权限（可覆写）

开发者
  └── 自己创建的 Agent: owner
  └── 他人分享的 Agent: 取决于 ACL 设置

成员
  └── 可见范围内 public + 被授权的 Agent
```

## 6. 桌面应用决策建议

### 6.1 问题

> 需求第 7 点: "待决策：是否需要桌面应用做本地隔离 vs 服务器沙箱"

### 6.2 决策框架

从 **用户价值 / 投入产出比** 维度分析。三项核心评估指标:

1. **用户价值增量**: 这个功能解决了什么不可替代的问题？
2. **工程投入成本**: 开发、测试、维护、分发成本
3. **风险与副作用**: 安全、版本碎片化、支持成本

### 6.3 评估结论

| 评估维度 | 评分 (1-10) | 说明 |
|---------|:----------:|------|
| 用户价值增量 | **4/10** | 对 MVP 目标用户(企业管理员+员工)来说，Web 端已满足核心需求 |
| 工程投入成本 | **8/10** (高) | 需维护桌面端 CI/CD、多平台打包、自动更新、本地沙箱安全 |
| 风险与副作用 | **7/10** | 安全边界模糊化、版本碎片化、离线审计盲区 |

### 6.4 理由详解

#### 为什么 MVP 阶段不做？

1. **价值错配**: MVP 用户的核心需求是"在浏览器里用 AI 助手"，而非"在本地跑 AI 任务"。桌面应用解决的"本地文件操作、离线执行"场景，大企业合规部门初期根本不会开放。

2. **安全是 Cloud-Native 的自然结果**: 服务器沙箱（gVisor/Firecracker）在隔离性、审计性、可管理性上全面优于桌面端。企业客户的第一优先级是"数据不离开我们的控制范围"，而非"在本地执行"。服务器沙箱更符合企业信任模型。

3. **资源聚焦**: 团队有限资源应该集中在核心价值链——Agent 创建体验、对话质量、知识库效果。桌面端会分散后端核心能力的打磨节奏。

4. **实验驱动验证**: 在不知道 Agent 是否有 PMF（产品市场匹配）之前，不应投入高成本的桌面端。先验证"企业是否需要 AI 员工"这个假设。

#### 什么时候值得做？

| 触发条件 | 说明 |
|---------|------|
| 客户明确需求 > 5 家企业客户要求本地执行 | 市场需求验证 |
| Agent 技能生态需要本地文件操作 | 如"帮我处理本地的 Excel 报表" |
| 低延迟场景成为核心场景 | 如实时语音 Agent 需要 <10ms 响应 |
| PMF 验证通过，商业化已有收入 | 有资金和人力投入 |

### 6.5 推荐方案

**MVP 阶段: 纯服务器沙箱 (gVisor)**

```
优势:
  ✅ 完全可控的安全边界
  ✅ 零客户端分发成本
  ✅ 统一版本管理
  ✅ 全量审计日志
  ✅ 与云原生架构一致
```

**后续阶段: 混合架构（看客户需求驱动）**

```
Phase 2 (3-6月): WASM 轻量沙箱 (服务器端)
  - 纯计算任务走 WASM，成本降低 40-60%
  - 无需桌面端

Phase 3 (6-12月): 桌面运行时 (企业版可选)
  - Tauri 2.0，Rust 内核 < 50MB
  - 仅限本地文件操作场景
  - 所有执行强制审计回传
  - 定价: 企业版付费功能
```

### 6.6 总结

> **不做。MVP 阶段专注 Web + 服务器沙箱。**  
> 桌面应用在早期阶段是"延迟满足"的典型例子——它能满足的想象空间很大，但解决的实际问题很少。如果 6 个月后 20% 的客户反馈"没有桌面端我们不买"，那再投入做也来得及。信息效率原则告诉我们：先做 Web 端把核心链路跑通，用最低成本验证产品价值。
